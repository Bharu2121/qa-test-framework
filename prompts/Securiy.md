# Security & API Test Enhancement Prompt

## Goal

Update the existing Admin Panel and Profile/Authentication API test framework.

Do NOT disturb the existing application functionality or existing test structure.

Add security-focused test cases for authentication, password management, JWT, logout, and API security.

---

## 1. Admin Panel - Forgot / Reset Password

Add test cases for the complete forgot-password flow.

### Test Cases

- Verify Forgot Password option is available.
- Verify valid registered user can request password recovery.
- Verify recovery key/token is generated and accepted correctly.
- Verify invalid recovery key is rejected.
- Verify expired recovery key is rejected.
- Verify already-used recovery key cannot be reused.
- Verify new password and confirm password must match.
- Verify weak/invalid passwords are rejected.
- Verify successful password reset with a valid recovery key.
- Verify old password cannot be used after successful reset.
- Verify new password can be used for login after reset.
- Verify password reset API does not expose sensitive information.
- Verify recovery key/token is not exposed in logs, UI, or API responses unnecessarily.

---

## 2. Update Password - Profile Page

Add tests for changing password from the Profile page.

### Test Cases

- User must enter the correct current password.
- Incorrect current password must be rejected.
- New password must satisfy password rules.
- New password and confirm password must match.
- New password should not be the same as the current password.
- Successful password update should invalidate the old password.
- Successful password update should allow login with the new password.
- Password should never appear in plain text in API responses or logs.

---

## 3. Password Security - bcrypt

Verify password storage/security at the API/backend level.

### Test Cases

- Password must never be stored as plain text.
- Password should be stored using bcrypt or the configured secure password-hashing mechanism.
- Verify password verification works with the correct password.
- Verify incorrect password is rejected.
- Never log or expose the original password.
- Do not add hardcoded real passwords or secrets to test code.

Do not modify production password hashes just for testing.

---

## 4. JWT Security

Add JWT-related security tests.

### Test Cases

- Verify successful login returns a valid JWT when JWT authentication is used.
- Verify protected API fails without a JWT.
- Verify invalid JWT is rejected.
- Verify expired JWT is rejected.
- Verify malformed JWT is rejected.
- Verify modified/tampered JWT is rejected.
- Verify JWT is not unnecessarily exposed in API responses or logs.
- Verify logout/session invalidation behavior according to the application's authentication design.
- Verify protected Admin APIs cannot be accessed with a token belonging to an unauthorized user/role.

Do not attempt real-world token theft or attacks.
Use only tokens generated by the test environment.

---

## 5. Logout

Add logout test cases.

### Test Cases

- Verify logged-in user can logout successfully.
- Verify logout API returns the expected response.
- Verify session/token is invalidated according to the application's design.
- Verify protected APIs cannot be accessed after logout when token invalidation is supported.
- Verify user is redirected to/login screen after logout where applicable.
- Verify browser refresh does not restore an authenticated session unexpectedly.
- Verify another user's protected data cannot be accessed after logout.

---

## 6. Login Security / Multiple Incorrect Attempts

Add controlled negative login tests.

### Test Cases

- Verify incorrect password is rejected.
- Verify incorrect username/email is rejected.
- Verify repeated incorrect login attempts are handled according to the application's security policy.
- Verify account lockout/rate limiting/captcha/security response if implemented.
- Verify the API does not reveal whether a username/email exists through different error messages.
- Verify successful login works after the configured security restriction is cleared.

Use a small controlled number of test attempts only.

Do NOT perform brute-force attacks or high-volume password guessing.

---

## 7. API Security Validation

For all authentication/password-related APIs verify:

- Authentication is required for protected endpoints.
- Authorization/role validation is enforced.
- Invalid request bodies are rejected.
- Missing required fields are rejected.
- Invalid data types are rejected.
- Sensitive information is not returned unnecessarily.
- Passwords, recovery keys, JWTs, and secrets are not written to logs.
- Appropriate HTTP status codes are returned.
- Error messages do not expose internal implementation details.
- User cannot update another user's password without proper authorization.
- Admin APIs cannot be accessed by normal users unless explicitly allowed.

---

## 8. Security Test Data

Use dedicated test users only.

Create separate test data for:

- Admin user
- Normal user
- Invalid user
- Locked/restricted user if supported
- Password reset user

Never commit real credentials, tokens, JWT secrets, recovery keys, or production data.

Use environment variables/configuration for sensitive test data.

---

## 9. Test Reports / Results Cleanup

Important:

When tests are executed, DO NOT keep unlimited historical reports inside the project.

Before generating a new test report:

1. Remove the previous test report/results.
2. Remove old screenshots/traces/videos if they belong to the previous run.
3. Generate the new test results.
4. Keep ONLY:
   - Latest test report
   - Current test results
   - Current failure screenshots/traces/videos if generated

Do not delete source code, test cases, configuration files, or test data.

The report directory should always represent the latest/current test execution only.

Example:

reports/
  latest/
    report
    results
    screenshots
    traces

Do not maintain:

reports/
  run-001/
  run-002/
  run-003/
  run-004/

unless historical reporting is explicitly required.

---

## 10. Implementation Requirements

Follow the existing project architecture.

Before adding files:

- Inspect the current API framework.
- Reuse existing API clients/utilities.
- Reuse existing authentication helpers.
- Reuse existing test data utilities.
- Follow the current naming conventions.
- Do not duplicate existing functionality.
- Keep security tests separate and clearly identified.
- Add appropriate tags such as `@security`, `@auth`, `@password`, or the project's existing tagging convention.
- Keep tests maintainable and readable.

After implementation:

1. Run the existing tests.
2. Run the new security tests.
3. Verify Admin forgot/reset password flow.
4. Verify Profile update-password flow.
5. Verify bcrypt/password handling.
6. Verify JWT validation.
7. Verify logout.
8. Verify controlled repeated-login negative tests.
9. Verify API authorization.
10. Verify old reports are cleaned before the new report is generated.
11. Confirm only the latest/current report remains.

Do not remove or break existing tests.

At the end, provide a simple summary:

- New security test cases added
- APIs covered
- Files created/updated
- Tests passed/failed
- Location of latest report
- Confirmation that previous test reports were cleaned
